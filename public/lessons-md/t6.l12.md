# T6.L12 — Attention–FFN Disaggregation: Splitting Inside the Layer

_Track T6: Mega-Scale Serving · ~30 min · kernelspace_

> P/D disaggregation split a request in time. Attention–FFN disaggregation splits every decode layer in space: attention keeps the KV cache, the experts get their own GPUs, and micro-batches cross the network twice per layer.
T5.L9 split prefill from decode, and T6.L3 added an encode fleet in front. Both cut a request into phases that run one after another. **Attention–FFN disaggregation (AFD)** cuts somewhere new: inside each decode layer. Attention runs on one pool of GPUs, the FFN (for an MoE model, the experts) on another, and every layer of every decode step hands the hidden states across and back.

The reason is that the two halves of a decode layer want different machines:

- **Attention** reads each sequence's own KV cache. Nothing is shared between sequences, so a bigger batch does not amortise those bytes. It is bound by HBM bandwidth and capacity, and its cost grows with context length.
- **The FFN** reads weights that every token shares, so batching amortises them. A dense FFN gets the whole batch. An MoE layer splits the batch among its experts: each expert sees about batch × top-k ÷ experts tokens.

That split is what starves MoE decode. MegaScale-Infer's own example: an A100 needs about 312 TFLOPS ÷ 2 TB/s = 156 tokens per weight read to be compute-bound. A batch of 156 on a top-2-of-8 model gives each expert 156 × 2 ÷ 8 = 39 tokens, so the experts run at about 39 ÷ 156 = 25 % of peak. More sequences per GPU would help, but each one also brings its KV cache, and HBM runs out first.

---

## Pool the tokens, not the cache

AFD runs attention data-parallel on many GPUs, each holding its own sequences and their KV. Their tokens all go to a small pool of FFN GPUs, which see the **sum** of the attention side's batches. The FFN pool is sized to compute; the attention pool is sized to memory. Neither has to compromise for the other, and each can use different hardware: MegaScale-Infer put attention on memory-rich H20s and experts on compute-rich L40S, and NVIDIA's [Vera Rubin platform](https://developer.nvidia.com/blog/inside-nvidia-groq-3-lpx-the-low-latency-inference-accelerator-for-the-nvidia-vera-rubin-platform/) runs attention and KV on Rubin GPUs while Groq 3 LPX runs the FFN and MoE layers.

Two papers report what the split bought, each on its own hardware and each against its own baseline:

---

- **4,039 tok/s/GPU** — Step-3 decode, 50 ms TPOT (Claim bench.step3.afd-decode: Hopper, FP8, 4K context, no MTP, 32 GPUs; the peak minute (3,910 long-term). arXiv 2507.19427v1.)
- **2,324 tok/s/GPU** — DeepSeek-V3, same setup (Claim bench.step3.dsv3-decode: DeepSeek's published profile with expert parallelism on 128 H800s, as the Step-3 paper cites it.)
- **up to 1.90×** — MegaScale-Infer per GPU (Claim bench.megascale-infer.per-gpu: the 317B Scaled-MoE on Ampere, BF16, at a 150 ms time-between-tokens target, against TensorRT-LLM. arXiv 2504.02263v4.)

---

## The ping-pong pipeline

A token cannot skip ahead: it needs layer *n*'s attention, then layer *n*'s experts, then layer *n + 1*'s attention. With one batch, the FFN pool idles while attention runs, attention idles while the experts run, and both idle while the hidden states cross the network. The fix is T6.L2's dual-batch overlap, stretched across two pools: split the batch into **micro-batches** and keep them in flight, so one computes on each side while another is on the wire.

How many are enough? MegaScale-Infer derives it. Let T_f be one micro-batch's compute time on the slower side and T_c one crossing. Both sides stay busy when m × T_f ≥ 2 × (T_f + T_c), so m ≥ 2 × (1 + T_c ÷ T_f). A fast fabric (T_c under half of T_f) needs 3 micro-batches; a slower one needs 4. Two never suffice, since every micro-batch spends time on the wire in both directions.

The pipeline raises throughput. It does not make a token faster: each micro-batch still waits for its own two crossings in every layer, and MegaScale-Infer notes that the pipeline can even add latency. That is why the papers state their SLOs, and why Step-3 budgets them. At a 50 ms time per output token (TPOT) with a three-stage pipeline (attention, the network, the FFN), each stage gets 50 ÷ 3 ≈ 16.6 ms per token step, and over Step-3's 61 layers that is 16.6 ÷ 61 ≈ 272 µs per layer for every stage, the network crossing included.

## Sizing the two pools

Step-3 serves a 4K average context with **2A2F**: two attention instances and two FFN instances, 32 GPUs. It runs 6,144 sequences as three micro-batches of 2,048. As a check on the claim: 6,144 sequences each emitting a token every 50 ms is 122,880 tok/s, or 3,840 per GPU; the reported 3,910 average and 4,039 peak minute need steps a little under 50 ms at that batch.

Longer context changes one side only. At 8K each sequence's attention reads twice the KV, so Step-3 doubles the attention instances and leaves the FFN alone: **4A2F**, 48 GPUs, the same 6,144 sequences, the same per-step work for the experts and the same network traffic. Total throughput stays put, so per-GPU throughput falls to about 4,039 × 4 ÷ 6 ≈ 2,690 (the paper measured 2,643). At 32K the same rule gives 16A2F and about 4,039 × 4 ÷ 18 ≈ 900.

That is T6.L3's sizing rule again: give each pool workers in proportion to the work it does. There it sized prefill against decode, and the items below practise it on fresh numbers before you size attention against the FFN.

_AFD ≡ compute/storage separation in databases_

- **storage tier** (Holds the data; sized on capacity and bandwidth (Aurora's storage fleet, Snowflake's object store).) ≡ **attention pool** (Holds each sequence's KV cache; sized on HBM capacity and bandwidth, and grown as context grows.)
  - where it breaks: A storage tier hands pages to the compute that asked for them; the attention pool keeps its KV where it is and runs attention there, so the state stays put and the work comes to it.
- **compute warehouses** (Stateless query workers sized on CPU, added or removed without moving data.) ≡ **FFN / expert pool** (Holds weights and no per-request state; sized on FLOPs once enough tokens are pooled.)
  - where it breaks: A warehouse runs whole queries on its own schedule; the FFN pool is a stage of every layer of every decode step, so its time per micro-batch must match the attention side's or one of them idles.
- **double buffering** (Fill one buffer while the other drains, so I/O hides under compute.) ≡ **ping-pong micro-batches** (Micro-batches alternate between the pools, so one computes on each side while another crosses the network.)
  - where it breaks: Two buffers hide one transfer; a micro-batch crosses twice per layer, so the pipeline needs at least three in flight (four on a slower fabric), and it adds latency to each token while it raises throughput.

**Where does it break? Attention–FFN disaggregation is mapped onto compute/storage separation in databases. Where does that mapping break?**

- (o1) The two tiers grow apart, and longer contexts add attention GPUs while the FFN pool keeps the same number of GPUs as before
- (o2) The stateful tier is sized on capacity and bandwidth, and the attention GPUs are sized on their KV cache and HBM bandwidth
- (o3) Stateless compute can serve many clients at once, and one FFN GPU serves the tokens pooled from several attention GPUs
- (o4) A query pulls pages over the network to compute, and AFD keeps KV and weights in place and sends activations each layer

**Principle:** Separate the state-bound tier from the compute-bound one and scale each on its own bottleneck. Databases carry over, but AFD moves small per-token activations twice per layer, so fabric latency sits on every token's path.

## When the hop eats the gain

Every layer of every decode step now crosses the network twice: Step-3 sends FP8 hidden states to the FFN pool and gets BF16 results back. That per-layer, per-token activation exchange needs a very low-latency fabric. Step-3 wrote its own GPUDirect RDMA library (StepMesh) to meet its 272 µs per-layer budget without giving any of the GPU's SMs to communication, and MegaScale-Infer wrote an M2N library that it measured at 68.2 % lower latency than NCCL. The split pays off for **MoE decode at scale**, where the experts are starved for tokens. It does not pay for a small dense model: its FFN already sees the whole batch, and a GPU or an NVLink node that runs both halves needs no network hop at all.

---

**Q1. Why does MoE decode gain from putting attention and the experts on separate GPUs?**

- (o1) Decode attention is compute-bound, and moving it off the expert GPUs frees their tensor cores for the attention math
- (o2) Each expert gets a small slice of a GPU's tokens, and pooling many attention GPUs' tokens fills each expert's batch
- (o3) Splitting removes the all-to-all from every layer, and tokens no longer cross the network between the two halves
- (o4) Expert weights cannot sit beside a KV cache, and splitting the layer is what lets an MoE model load onto its GPUs

**Q2. MegaScale-Infer splits each batch into micro-batches that alternate between the attention and FFN GPUs. What does that buy, and what does it cost?**

- (o1) Two micro-batches keep both pools busy, as with a double buffer, and a third one adds overhead to each step
- (o2) Both pools keep computing while other micro-batches cross the wire, and a token's own step gets no faster
- (o3) The micro-batches stay inside one node, and the FFN pool no longer waits on the network between the layers
- (o4) Each token's step gets faster as the hops overlap, and the GPUs need fewer of them to serve the same traffic

**Q3. Step-3 serves a 4K context with 2 attention and 2 FFN instances of 8 GPUs at 4,039 tok/s per GPU. At 8K, attention reads twice the KV per sequence. Keeping the batch and the SLO, which deployment does the paper choose?**

- (o1) 4 attention and 2 FFN instances, 48 GPUs, about 2,690 tok/s per GPU
- (o2) 4 attention and 4 FFN instances, 64 GPUs, about 2,020 tok/s on each GPU
- (o3) 2 attention and 4 FFN instances, 48 GPUs in all, about 2,690 tok/s per GPU
- (o4) The same 2 and 2 instances on 32 GPUs, about 2,020 tok/s per GPU

**Q4. Which deployment is least likely to gain from attention–FFN disaggregation?**

- (o1) A fleet whose context lengths keep growing, where attention needs more GPUs while the expert pool does not
- (o2) A large sparse MoE model in decode at high load, where each expert sees few tokens from any one GPU
- (o3) A small dense model on a single node of GPUs, where its feed-forward layers already see the whole batch
- (o4) A cluster with memory-rich GPUs and compute-rich GPUs, where each pool can take the hardware it suits

The two headline numbers are not one comparison. MegaScale-Infer's 1.90× is decode throughput per GPU for its 317B Scaled-MoE on 80 GB Ampere GPUs in BF16, at a **150 ms** time-between-tokens target, against TensorRT-LLM (7.11× against vLLM; 1.28× over TensorRT-LLM on Mixtral 8x22B). The Step-3 paper itself points at the gap: a 150 ms token is too slow for chat. A looser latency target lets a system run bigger batches and deeper pipelines, so before you compare two disaggregation results, line up the SLO, the precision, the context length and whose run the baseline was.
