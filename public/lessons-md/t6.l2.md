# T6.L2 — Wide Expert Parallelism in Production

_Track T6: Mega-Scale Serving · ~30 min · kernelspace_

> EP144 means your batch is spread across 144 GPUs and every layer is a distributed transaction. DeepEP, EPLB, and communication-computation overlap are the machinery that keeps it profitable — and SGLang reproduced the whole thing on 96 H100s for you to read.
T6.L1 gave you the problem: hot experts straggle the combine barrier, and MoE wants huge batches. **Wide EP** is the production answer: spread the experts across *many* GPUs (EP32 for prefill, EP144 for decode in the layout DeepSeek published for its V3/R1 service), run enormous batches so expert utilization is uniform, and hide the all-to-all behind compute. This lesson is the three mechanisms that make it work — and the one public reproduction you can study line by line.

Why EP32 for prefill but EP144 for decode? The phases have opposite physics again (T5.L3): prefill is compute-bound — moderate EP, big per-GPU chunks, dense tensor-core work. Decode is bandwidth-bound and latency-critical — spread experts maximally (EP144), because each GPU then holds *fewer* experts and reads *less* weight per step... and because only a giant batch keeps 256 experts uniformly fed.

---

## Mechanism 1: DeepEP — the dispatch/combine library

The all-to-all is so central that DeepSeek open-sourced a dedicated library for it, in February 2025, on day 2 of its Open-Source Week. This section describes the library's first interface, V1, because the trade it teaches is the lasting part. V1 had two kernel sets, since the two phases want different things:

- **Normal kernels** (prefill/training): maximize bandwidth. Aggregate tokens by destination, forward over NVLink and RDMA with big transfers, tolerate microseconds of latency.
- **Low-latency kernels** (decode): minimize latency at smaller transfer sizes. DeepEP's V1 README calls them "a set of low-latency kernels with pure RDMA to minimize delays", for latency-sensitive decoding.

**The API has moved since** (one EPBuffer interface for high-throughput and low-latency EP; V1 removed as of DeepEP f6aa38f, read 2026-11-22). DeepEP's current README says its V2 unified "High-throughput and low-latency APIs ... into a single `EPBuffer` interface", and that its V2.5 release "Fully remove[d] V1". Training, prefill and decode now call the same dispatch and combine. The bandwidth-versus-latency trade did not go away; it moved inside the library, which estimates the SM and QP counts itself. Read the repository's README for the interface you would install today.

This is a recurring systems lesson: *one fabric, phase-specific paths*. Your batch-vs-streaming instinct, your bulk-vs-interactive RPC instinct — same shape. The transport is shared; what you optimize depends on the phase.

## Mechanism 2: EPLB — load balance as a packing problem

The **Expert Parallel Load Balancer** treats hot experts as a bin-packing problem. Estimate per-expert load (the repository leaves the predictor out of scope; "A common method is to use moving average of historical statistics"); **replicate** the hottest experts as "redundant experts" onto other GPUs (replication, not migration — the weights are small compared to the KV); then **pack** the copies onto GPUs heuristically, so the combine barrier costs about the mean load, not the max.

Notice what EPLB really is: **replication plus bin-packing, with no hashing in it**. Placement is computed from measured load, not from a hash of the expert id: that is the difference from your cache tier (T3.L6, T5.L9), where a hash fixes which node owns a key and load follows. Here load comes first and placement follows. DeepSeek's repository ships two policies: a *hierarchical* one for prefill, at a smaller expert-parallel size, that packs expert groups onto nodes first, and a *global* one for decode, at a larger size, that replicates across all experts and packs the copies onto GPUs.

## Mechanism 3: overlap — hide the network under compute

Even with DeepEP, the all-to-all costs real microseconds. The fix is the oldest trick in the latency book (T2.L6): never wait. DeepSeek's **dual-batch overlap** splits a batch of requests into two micro-batches, in both phases. In *prefill* the two run alternately: while micro-batch A computes, micro-batch B does its dispatch/combine transfer, and the cost of one hides behind the compute of the other.

*Decode* keeps the two micro-batches and schedules them differently. DeepSeek writes that "the execution durations of different stages are unbalanced", so it subdivides the attention layer into two steps and runs "a 5-stage pipeline" for the overlap. Its profiling notes add that decode's all-to-all "does not occupy GPU SMs": after the RDMA messages are issued "all GPU SMs are freed", and the system waits for the transfer only after the computation has finished. In both phases the all-to-all leaves the critical path — not removed, hidden.

The same pattern appears as DualPipe in training and as "PDL" (programmatic dependent launch) in NVIDIA's decode optimizations. When you see compute and communication alternating, overlap them. When you see a barrier, ask what could have been running during it.

The genuinely new thing is only the payload: tokens instead of requests, experts instead of shards.

**Q1. Decode runs at EP144 while prefill runs at EP32 primarily because…**

- (o1) Decode needs more FLOPs per token than prefill, demanding many more GPUs to finish each step within its latency budget
- (o2) The width matches the number of experts per layer in the model, with prefill simply using fewer of them
- (o3) Decode is bandwidth-bound and wants huge uniform batches, while prefill is compute-bound and wants big dense chunks
- (o4) Prefill cannot use the dispatch path efficiently, confining it to a narrow group of GPUs in one NVLink domain

**Q2. EPLB keeps the combine barrier cheap by…**

- (o1) Capping each expert's capacity and dropping tokens past the cap, leaving no GPU above the average load
- (o2) Shrinking the batch at each step to send fewer tokens to any expert, flattening load at some cost in utilization
- (o3) Replicating hot experts onto second GPUs and reassigning placement, leaving each GPU near the mean load
- (o4) Detecting slow GPUs at runtime and rerouting their tokens to next-best experts, leaving the barrier waiting on healthy devices

**Q3. Dual-batch overlap exists to…**

- (o1) Pipeline two micro-batches, letting one compute while the other communicates and hiding network time behind compute
- (o2) Replicate each expert on two GPUs, letting a token use whichever copy is idle and skipping the dispatch wait entirely
- (o3) Run two model copies on one GPU, letting a new version be tested against the old without a restart
- (o4) Double the batch per step, flattening expert load statistically at the cost of extra latency per generated token

**Q4. DeepEP's first release shipped separate high-throughput and low-latency kernel sets because…**

- (o1) One mode moves tokens within a node over the fast local links, while the other moves them across nodes over the slower network fabric
- (o2) The low-latency mode replaced a buggy original, while the older mode stays for compatibility with earlier deployments
- (o3) Training and inference use different expert layouts, while each needs a routine matched to its weight format
- (o4) Prefill wants bandwidth from large batched transfers, while decode wants the least delay from small per-step transfers
