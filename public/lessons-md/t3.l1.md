**P1. `let b = a;` for an owning type (String, Vec) in Rust…**

- (o1) Creates an immutable borrow of a that leaves a readable but forbids mutating it
- (o2) Copies the heap buffer into a second allocation that b owns independently of the original a

**P2. The borrow rule "many &T XOR one &mut T" directly prevents…**

- (o1) Iterator invalidation and data races by letting no one mutate while any readers exist

- (o3) Deadlocks by giving a value exclusive access that stops threads waiting on each other
- (o4) Out-of-bounds indexing panics by making a borrowed slice carry its own length

**P3. A function builds a String local to its body and returns `&s` pointing at it. The compiler rejects the function because…**

---

R3, R4 and R9 taught the three rules, and the four questions above asked for them from memory. This lesson does not teach them again. It asks what they cost when your data is not a tree.

Ownership gives every value exactly one owner, so owned data forms a tree: follow the owner links and you never loop back. A doubly-linked list, a graph, a cache with parent pointers or a map that several threads update is not a tree. Systems Rust has three tools for those shapes, and each one trades a compile-time guarantee for a cost you pay somewhere else. T3 starts by pricing them.

---

## What R already settled

Three rules carry into everything below. Each has its own lesson if a question above missed.

- **Moves (R3):** one owner, one drop. Assigning an owning value moves it, and the old binding is statically dead.
- **Borrows (R4):** many `&T` or one `&mut T`, never both, for as long as a borrow lives. That is what rules out iterator invalidation and data races.
- **Lifetimes (R9):** an annotation is a contract between inputs and outputs, checked at every call. It never keeps data alive.

Together they prove that no reachable path can observe a dead value or a conflicting mutation. The proof is conservative, and it has a shape: **ownership edges form a tree.** That is the wall newcomers hit on lists with back-pointers, graphs and shared caches, and the three exits below are how systems code goes around it.

---

## Graphs without leaks: the arena first

The first exit keeps single ownership and removes the pointers. One `Vec` owns every node, and a "link" is a `usize` index into it. Indices are not borrows, so there is nothing for the checker to fight, and a cycle is just two numbers that name each other. Your T1 allocator hands out offsets into a slab in the same way, and the layout is the one T0.L4 rewards: nodes sit densely in one array.

---

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
struct NodeId(usize);                    // a handle, not a borrow

struct Node {
    label: String,
    edges: Vec<NodeId>,                  // links are numbers
}

#[derive(Default)]
struct Graph {
    nodes: Vec<Node>,                    // the single owner of every node
}

impl Graph {
    fn add(&mut self, label: &str) -> NodeId {
        self.nodes.push(Node { label: label.to_string(), edges: Vec::new() });
        NodeId(self.nodes.len() - 1)
    }
    fn link(&mut self, from: NodeId, to: NodeId) {
        self.nodes[from.0].edges.push(to);   // a cycle is two numbers
    }
}

let mut g = Graph::default();
let a = g.add("scheduler");
let b = g.add("block manager");
g.link(a, b);
g.link(b, a);        // a cycle: compiles, and cannot leak
// dropping g frees both nodes: one Vec, one owner, one drop
```

---

The arena's price is paid at run time and in discipline. An index is only a number, so if you remove a node and reuse its slot, an old `NodeId` quietly names the new occupant: a dangling pointer by another name, and the same shape as the ABA problem in T2.L5. The fix is a **generation counter** stored beside each slot and inside each handle, which crates such as `slotmap` package up. Until you need deletion, a plain `Vec` is enough.

---

_fig 1 — a strong cycle of Rc leaks; one Weak edge breaks it_

Components: let a (the only variable) · Node A (strong count 1) · Node B (strong count 1) · Node C (strong count 1)

Steps:
1. A chain built from Rc: the variable a owns A, A owns B, B owns C. Each strong count is 1, and dropping a would free A, then B, then C.
2. Close the loop: C stores Rc::clone of A as its back-edge. A is now held by the variable and by C, so its strong count is 2.
3. The variable a goes out of scope, and A's count falls from 2 to 1, not 0. C still holds A, A holds B, B holds C, so every count stays above zero and nothing is ever freed. Safe Rust allows this: it is a leak, not a crash.
4. The fix is to make the back-edge a Weak (Rc::downgrade). A weak edge adds no strong count, so when a drops, A hits 0 and is freed, then B, then C. Following the weak edge later calls upgrade(), which returns None once its target is gone.

## Rc and RefCell: shared ownership, checked at run time

The second exit gives up single ownership. `Rc<T>` lets several owners share one value, freed when the last strong handle drops, and `RefCell<T>` lets you mutate through a shared handle by moving the borrow check from compile time to run time. Together they build the parent-and-child shape the arena avoids, with the tree's owning edges as `Rc` and the edges back up as `Weak`, exactly the fix in fig 1.

---

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Node {
    label: &'static str,
    children: RefCell<Vec<Rc<Node>>>,    // owning edges point down the tree
    parent: RefCell<Weak<Node>>,         // the edge back up must not own
}

let leaf = Rc::new(Node { label: "leaf", children: RefCell::new(vec![]), parent: RefCell::new(Weak::new()) });
let root = Rc::new(Node { label: "root", children: RefCell::new(vec![Rc::clone(&leaf)]), parent: RefCell::new(Weak::new()) });
*leaf.parent.borrow_mut() = Rc::downgrade(&root);   // weak: no strong count added

// Rc::strong_count(&root) == 1 and Rc::weak_count(&root) == 1
// drop(root) frees root; leaf.parent.borrow().upgrade() is now None
```

---

The price: every clone and drop of an `Rc` updates a plain integer count, and every `borrow_mut()` checks a flag. A conflicting borrow is no longer a compile error. It is a **panic** at the moment two borrows overlap, which means the bug moves from your build to your test suite, or to production. And `Rc` is neither `Send` nor `Sync`, so this shape cannot leave its thread (T3.L3).

---

## Arc and Mutex: the same shape across threads

The third exit is the same idea made thread-safe: `Arc<T>` counts with atomic operations, and `Mutex<T>` makes a second locker wait instead of panicking. It is the `Rc<RefCell<T>>` of threaded code.

---

```rust
use std::sync::{Arc, Mutex};
use std::thread;

// One lock around the whole arena: simple, correct, serialises every access.
let g = Arc::new(Mutex::new(Graph::default()));
let handles: Vec<_> = (0..4).map(|i| {
    let g = Arc::clone(&g);                    // an atomic count bump per handle
    thread::spawn(move || {
        let mut graph = g.lock().unwrap();     // waits while another thread holds it
        graph.add(&format!("worker-{i}"));
    })                                         // the guard drops here: unlocked
}).collect();
for h in handles { h.join().unwrap(); }

// A Mutex per node allows parallel edits, and adds a rule you must keep:
// take node locks in one global order (say, by NodeId), or two threads that
// lock a then b, and b then a, can wait on each other forever.
```

---

Pairing an arena with one lock is the usual first design for threaded graphs: the cycle problem stays solved, and the only question left is how coarse the lock is.

---

## What each one costs

| | Arena (`Vec` plus indices) | `Rc<RefCell<T>>` | `Arc<Mutex<T>>` |
|---|---|---|---|
| Threads | any, with one owner | one thread only | many threads |
| Handle clone and drop | a copy of an integer | a plain integer count | an atomic read-modify-write |
| Access check | bounds check on the index | borrow flag at run time | the lock, which waits |
| How it fails | a stale index names the wrong node | panic on overlapping borrows | deadlock from lock order, or a poisoned lock |
| Cycles | safe, no counts | leak unless an edge is `Weak` | leak unless an edge is `Weak` |

Read it as a ladder. Start with the arena: it has no counts and no hidden checks, and it keeps the data dense. Reach for `Rc<RefCell<T>>` only when ownership is genuinely dynamic on one thread, and for `Arc<Mutex<T>>` only when threads must share it. Each step down the ladder swaps a compile-time guarantee for a run-time check, so each step is a decision to write down, not a default.

---

> **[analogy]** On the JVM a tracing collector frees whatever the program can no longer reach, and CPython adds a cycle collector to its reference counts, so cycles never bothered you there. Rust has no tracer behind `Rc`, so a strong cycle is invisible and permanent. The price you never saw is the one you now choose: counts, checks and locks written into the types.

---

> **[warning]** Two traps catch most first designs. **A strong cycle in `Rc` or `Arc`** compiles, passes tests and leaks memory in a long-running service until something else fails; give every edge that points back up the tree a `Weak`. **A `borrow_mut()` held across a call that borrows again** compiles and then panics, so keep `RefCell` borrows to a single expression and never hold a guard while calling into code you do not control.

**Q1. The idiomatic systems-Rust answer to cyclic structures (graphs, linked lists) is…**

- (o1) Raw pointers between nodes inside an unsafe module that works around the borrow checker
- (o2) Rc<RefCell<...>> around each link as the drop-in replacement for a pointer
- (o3) An arena with one owning Vec and usize indices standing in for pointers between graph nodes
- (o4) Box<Node> links in both directions that each own their target node

**Q2. Two nodes each hold an Rc to the other, and the last variable pointing at either one goes out of scope. What happens to them?**

- (o1) Both nodes are freed in the order they were created, since dropping the last variable frees whatever it reaches
- (o2) The program panics at run time, because Rc detects the cycle as it drops and refuses to free either node
- (o3) The compiler rejects the program, because two owners that point at each other can never be proved safe
- (o4) Neither node is freed, because each keeps the other's strong count above zero and the leak is safe but lasting

**Q3. Moving a graph from Rc<RefCell<Node>> to Arc<Mutex<Node>> so worker threads can share it changes the price of sharing by…**

- (o1) Making every handle clone and drop an atomic update, and making a conflicting access wait for the lock instead of panicking
- (o2) Making reference cycles safe, because atomic counts let Arc free a cycle once every thread has stopped using it
- (o3) Nothing but the names, as both pairs count handles and check access in the same way and differ only in what the compiler allows
- (o4) Moving the access check to compile time, because a Mutex proves exclusion statically and no run-time flag remains

**Q4. An arena graph is shared by worker threads. Compared with one Mutex around the whole graph, giving every node its own Mutex…**

- (o1) Lets threads edit different nodes in parallel, so it adds a duty to lock in a fixed order or risk deadlock
- (o2) Removes the need for Arc, because a lock held inside each node lets the nodes be shared without any count
- (o3) Lets threads edit in parallel with no new risk, because each lock guards a single value and cannot join a cycle
- (o4) Trades safety for speed, because a lock per node lets two threads write the same node at the same moment
