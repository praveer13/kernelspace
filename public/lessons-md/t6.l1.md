# T6.L1 — The MoE Anatomy: Experts, Routers, and the All-to-All

_Track T6: Mega-Scale Serving · ~30 min · kernelspace_

> DeepSeek-V3 has 256 experts and uses 8 per token. That one design decision changes every system you have learned so far — the memory math, the batching, the network, the scheduler. This is why T6 exists.
Everything before this track assumed a dense model: every token touches every parameter, so every token costs the same weight-read (T4's roofline arithmetic). Mixture-of-Experts breaks that symmetry. The FFN layer — roughly two-thirds of a transformer's parameters — is replaced by **N parallel expert FFNs plus a tiny router network**. Each token, the router scores all N experts and sends the token to the top-k (DeepSeek-V3: N=256 routed experts + 1 shared, k=8). Total parameters: 671B. Parameters touched per token: ~37B.

The deal: dense-model quality at a fraction of the per-token weight bandwidth. T4's decode economics — tokens/s ≈ bandwidth ÷ bytes-per-token — suddenly divides by ~18 for the FFN part. That is why every frontier open model of 2025-2026 is an MoE (DeepSeek V3/R1, Kimi K2, Qwen3, Mixtral's descendants, gpt-oss).

---

## What the router costs you: the all-to-all

Here is the systems bill, and it is paid in *network*, not FLOPs. With more experts than one GPU holds, each expert lives on a specific device. After the router decides, **every token must be physically moved to the GPUs hosting its k experts**, computed there, and moved back. Per layer, per batch: a **dispatch** all-to-all (tokens → expert devices) and a **combine** all-to-all (results → home devices). A 256-expert model at expert parallelism 144 (EP144, DeepSeek's decode config) runs this across 144 GPUs — twice per MoE layer. DeepSeek-V3 has 61 layers, but the first 3 are dense FFNs with no router, so that is 58 MoE layers and 2 × 58 = 116 all-to-alls per forward pass.

This is why MoE serving is a *scheduling and networking* discipline:
- **Load balance is the whole game.** If 30% of tokens pick expert #7, expert #7's GPU is the straggler and 143 others wait at the combine barrier. Hot experts are the NCCL stall of T0.L6 writ large.
- **The batch is the load balancer's only material.** More tokens per forward = more uniform expert utilization = better GPU occupancy. MoE *demands* big batches — the exact opposite of low-latency small-batch serving, and the tension T6.L2 resolves.
- **Latency floor = network round-trip × 2 × layers.** On NVLink this is tens of microseconds; on RDMA it dominates. Topology stops being trivia and starts being the price list.

## MLA: the other half of the DeepSeek trick

T5.L4 taught you KV bytes/token = 2 × layers × kv_dim × bytes, and Llama-3-70B's 327,680 B/token (320 KiB). DeepSeek's **Multi-head Latent Attention (MLA)** rewrites that line: instead of caching per-head K and V, the model stores one shared low-rank **latent vector** per token *per layer* (~576 elements: a 512-dim compressed latent plus a 64-dim RoPE key) and reconstructs per-head K/V on the fly with small up-projection matrices. KV cache per token: 576 × 2 B (BF16) = 1,152 B per layer × 61 layers = **70,272 B (≈68.6 KiB)**, against 327,680 B (320 KiB) for Llama-3-70B — about 4.7× smaller. The "×smaller than MHA" figure needs a baseline: the same 70B with full MHA (64 KV heads, 2 × 80 × 8192 × 2 B = 2,621,440 B per token) would be ≈37× bigger than MLA's 70,272 B.

Run T5.L4's arithmetic again with 70,272 B per token: the "cache is the payload" conclusion intensifies *less*, long context gets ~4.7× cheaper than Llama-3-70B, and the EP144 decode fleet can hold the giant batches that expert load-balancing requires. MLA is not an optimization bolted onto MoE — it is what *enables* the batch sizes MoE wants. When you design a serving stack, per-token KV bytes is the first number you ask for, and "what attention variant?" is why you had to ask.

_MoE ≡ your microservice fleet_

- **one monolith: every request runs every code path** (Dense model: every token reads every weight.) ≡ **N sharded services behind a router** (MoE: a router sends each token to top-k specialist experts.)
  - where it breaks: A service router picks a shard once per request; the MoE router picks the top-k experts for each token at each MoE layer, and under expert parallelism each pick is a network trip (a dispatch and a combine all-to-all, 2 × 58 = 116 per forward pass in DeepSeek-V3).
- **hot partition → fleet-wide straggler** (One overloaded shard makes every fan-out request miss its p99.) ≡ **hot expert → combine-barrier stall** (One popular expert makes the whole batch wait at the all-to-all.)
  - where it breaks: A hot service shard can be hedged, retried elsewhere or split by key; a token's experts are fixed by the router and each lives on one GPU, so the remedies are bigger batches or EPLB copies of the hot expert, which cost HBM.
- **session affinity for cache locality** (Sticky routing so the same user lands on the warm shard.) ≡ **EP-aware batching / EPLB** (Shape traffic so experts stay balanced and tokens travel less.)
  - where it breaks: Session affinity trades balance for locality by pinning a user to one warm shard; EPLB trades memory for balance, copying hot experts onto more GPUs and packing the copies evenly, while the router still decides where each token goes.

**Where does it break? MoE is mapped onto a fleet of sharded services. Where does that mapping break?**

- (o1) A service router chooses one shard per request, and the MoE router chooses its top-k experts for each token at each MoE layer
- (o2) Sticky routing keeps related requests near their warm state, and EP-aware batching keeps tokens near the experts serving them
- (o3) A hot shard delays the whole fan-out request, and a hot expert delays the whole layer while other GPUs wait at the barrier
- (o4) A front-end router splits traffic so each shard sees part of it, and the MoE router splits tokens so each expert sees part of them

**Principle:** A fan-out runs at the speed of its slowest branch. In MoE the router decides per token, the network carries each decision, and the finish time of a layer follows the busiest GPU, not the average.

**Q1. The core inference-economic win of MoE is…**

- (o1) Shrinking the total parameter count a lot, letting the whole model fit on fewer GPUs and cost less to store and serve
- (o2) Replacing most attention layers with a cheap router lookup, cutting the quadratic attention cost on long prompts
- (o3) Quantizing expert FFNs harder than dense ones, reaching the same quality with far fewer bits per weight
- (o4) Running a small top-k subset of experts for each token, leaving active parameters far below the total capacity

**Q2. The all-to-all problem refers to…**

- (o1) Exchanging gradients across data-parallel replicas after each step, demanding a faster fabric than dense models
- (o2) Copying expert weights between GPUs after each router rebalance, stalling decode every time one happens
- (o3) Broadcasting the full router score matrix to each device, letting each GPU pick top-k experts for any token
- (o4) Sending tokens to their experts' GPUs and the results back twice per layer, adding network cost as depth grows

**Q3. MLA's contribution to serving economics is…**

- (o1) Fusing attention kernels to read the KV cache faster, finishing each decode step sooner at equal cache size
- (o2) Storing the KV cache at lower precision, halving bytes per token while the cache layout stays unchanged
- (o3) Caching one shared low-rank latent per layer, shrinking the KV cache and letting far bigger batches fit
- (o4) Skipping low-scoring attention heads with a learned gate, cutting both the attention math and the KV bytes

**Q4. A "hot expert" hurts because…**

- (o1) Replicating it onto a second GPU duplicates its weights, eating the memory the batch needed for cache
- (o2) Routing collapses toward it as other experts go cold, leaving the router to send tokens there regardless of content
- (o3) Its GPU runs out of memory for the cache, leaving requests preempted and each expert's batch smaller
- (o4) Its GPU becomes the straggler at the combine barrier, leaving the other devices waiting on the slowest expert
