# S5 · Fleet physics v2: spec (PRs s5a, s5b)

**Status:** draft for owner review; the build proceeds on the defaults below (S5-D27, S5-D28). **Date:** 2026-10-18. **Base:** `master` = 9aa27de, with all of Wave 3 merged (PR #19, `wave-3s`; `docs/specs/wave-3.md` holds D1–D79). Its tree is byte-identical to `wave-3s` at d31a770, where the S5 design read the code, so file:line citations below hold at 9aa27de; each names its symbol, which is the stable anchor, and line numbers are hints.
**Opened early.** PLAN-100X.md:706 dates S5's gate "not before 2027-10". The owner opened S5 on 2026-10-18 and chose, from Wave 4, only S5 and the pre-registered report outputs of wave-3 D65 (PR `wave-3x`, open beside this one). Every other Wave 4 item (the Device Mesh, the Throughput Factory and the rest of the table) keeps its gate and date, and nothing of them enters this spec.
**The plan's gate and default** (PLAN-100X.md:706, the Wave 4 table, quoted): "S5 physics v2 → step-time exercises, Device Mesh, Throughput Factory | η fitted on a subset of published points; leave-one-out error ≤15% per hardware row (SGLang's ~6% simulator is vendor-reported precedent only) | 2027-10 | v1 + generators". PLAN:336 sizes it "**S5 · Fleet physics v2 (L)**"; PLAN:674 costs code QA at "4, 8 or 20 h per S, M or L".
**Implements** PLAN §5.2 S5: a step-time physics for the Fleet on the rows the lessons use, a published-point gate that decides whether learners ever see it, and the default ("v1 + generators") whatever the gate says.
**Sources.** This spec is written from the S5 design (S5-D1–D26, synthesised from three candidate designs and an adversarial judgement) and its five readers (the v1 engine and its consumers, the claims registry, the plan and pedagogy, the published points, the model literature). They live in the orchestrator's scratchpad and are not committed. Numbers marked **[proto]** come from those prototype runs, not from the repo: the in-repo harness (S5-06, S5-07, S5-08) replaces every one of them, and its PR explains each difference above 2 points.
**Nothing but this file is committed with the spec.** PR s5a's first level commits the gate protocol (`docs/physics/protocol.md`) before any task fits anything in the repo.

Section numbers below are cited by the task DAG (§10) and by `s5-dag.json`.

## 3. The physics (S5-02)

### 3.1 What one step carries

A step is one engine iteration. Running sequences decode first, one token each. Prefill chunks then fill the rest of the step's token budget (the harness's 8,192, `status.inferencex.harness.batch-tokens`, S5-D34) in arrival order, up to `maxNumSeqs` sequences (vLLM V1 has "no prefill or decode phase", claim `twin.vllm.scheduler`). From the batch the card reads four integers:

| Field | Meaning | A decoding sequence at context c | A prefill chunk of p tokens after h already prefilled |
|---|---|---|---|
| `tokens` (T) | tokens computed this step | 1 | p |
| `kvTokens` (K) | KV entries read or written this step | c | h + p |
| `attnPairs` (A) | causal attention token pairs | c | p·h + p(p+1)/2 |
| `seqs` | sequences in the step | 1 | 1 |

Each field is summed over the batch. Every value stays below 2^53, so the sums are exact integers.

### 3.2 The card

```ts
// src/lib/world/physics/types.ts
export interface ChipShape { bwBps: number; peakFlops: number; hbmBytes: number }   // B/s, FLOP/s at the row's weight precision, bytes
export interface ModelShape { params: number; layers: number; hidden: number; kvBytesPerToken: number; weightBytes: number }
export interface CardParams { etaMem: number; etaFlop: number; layerUs: number; seqUs: number; linkGBs: number | null } // null: no link term
export interface CardSpec { chip: ChipShape; model: ModelShape; params: CardParams }
export interface StepLoad { seqs: number; tokens: number; kvTokens: number; attnPairs: number }
export interface StepCard {
  memBytes: number; flops: number; linkBytes: number      // per GPU
  memS: number; flopS: number; fixedS: number; linkS: number; stepS: number
  bound: 'mem' | 'flop'
  us: number                                               // the step's duration, integer µs
}
// src/lib/world/physics/card.ts
export const NAPKIN: CardParams = { etaMem: 1, etaFlop: 1, layerUs: 0, seqUs: 0, linkGBs: null }  // "the datasheet bound"
export function stepCard(spec: CardSpec, tp: number, load: StepLoad): StepCard
```

The operation order is part of the contract (the golden step vectors pin it):

```
memBytes  = (W + kv·K) / tp                                   W = model.weightBytes, kv = model.kvBytesPerToken
flops     = (2·params·T + 4·layers·hidden·A) / tp
linkBytes = tp > 1 ? (2·layers·T·hidden·2·2·(tp − 1)) / tp : 0   two ring all-reduces of BF16 activations per layer
memS      = memBytes / (etaMem · bwBps)
flopS     = flops / (etaFlop · peakFlops)
linkS     = linkGBs === null || tp === 1 ? 0 : linkBytes / (linkGBs · 1e9)
fixedS    = (layers · layerUs + seqs · seqUs) / 1e6
stepS     = fixedS + linkS + Math.max(memS, flopS)
us        = Math.round(stepS · 1e6)                           bound = memS ≥ flopS ? 'mem' : 'flop'
```

- `ChipShape` and `ModelShape` are built from claims with `claimNumber(id, scale)` exactly as Boot builds its inputs (`claimNumber(id, 1e12)` for TB/s and TFLOP/s, `1e9` for GB and B params; `src/lib/boot/model.ts`, `bootInputs`). The engine never calls `claimNumber` (I3): `table.ts` stores the built shapes.
- The engine's step duration is exactly `card.us`. `EngineV2` keeps the last card (`lastCard`), so a panel can print the step it ran.
- **The napkin pin (S5-D38).** With `NAPKIN`, tp 1, T = 1, K = Boot's `chats × CHAT_TOKENS`, Boot's own chip and model (BF16 Llama-3-8B, 2 B per weight), `memS` === `deriveBoot().stepSeconds`, and with K = 0 `memS` === `tokenSeconds`. `kv.ts`'s `itlMs` (its fixtures) and `roofline` `decode-b1` answers agree to 1e-12 relative. No caller changes.

### 3.4 What is validated, and what is not

- **Validated: predictions.** TPOT per published configuration (G1, G2); TTFT on prefill-dominated configurations (G3); each graded decision quantity on published pairs (H1, §7.0).
- **Not validated: the split between terms.** The same data read by three equally good forms [proto]:

  | | form A ("minimal") | form B ("faithful") | the card |
  |---|---|---|---|
  | H100 bandwidth efficiency | 0.74 | 0.96 (at its bound) | 0.86 |
  | H100 fixed cost per step at TP 2 | 2.23 ms | 6.18 ms | 5.79 ms |
  | B200 bandwidth efficiency | 0.93 | 0.62 | 0.84 |

  All three score TPOT LOO mean 3–5 %. Within the card the refit ranges are narrow (η_m 0.87–0.90 on H100); that is precision within one form, not identification across forms.
- **Consequences.** No item grades a learner on a fitted value. The tab prints each parameter with "this fit's split; refit range x–y; other equally good forms split it differently", plus the table above. `hardware.ts:45` and `decode-kv.ts:154` point to the tab and tell no reconciliation story. A scene may *show* the card's parameters as "the engine's numbers", so a learner can work the card; it never presents them as hardware facts.

### 3.5 What the card leaves out (the tab lists these)

Speculative decoding and MTP; MoE routing and EP all-to-all; CUDA-graph batch buckets; tile and wave quantisation; attention-kernel path changes (sliding window, MLA); clocks and thermals; preemption cost (the box excludes it); prefix caching (the harness ran with it off); disaggregated KV transfer; multi-node; any model, precision, engine release or token budget other than the row's.

### 3.6 Worked example A: a decode step (H100 · FP8, TP 4, 4 users, ~1k prompts, ~1k outputs)

**Published.** InferenceX id **41187**, raw member `"mean_tpot":0.011776147370379336`, so **11.776 ms**; run https://github.com/SemiAnalysisAI/InferenceX/actions/runs/18924448230/attempts/2; pinned query in §4.1. The parameters are the all-points prototype values (η_m 0.86, η_f 0.50, t_layer 68.8 µs, t_seq 69.0 µs, β 231 GB/s) [proto]; the arithmetic is the contract S5-02's test pins from these given values. Re-derived for this spec in the operation order of §3.2:

1. **Lengths.** The harness draws lengths uniformly on the integers [⌊0.8 × 1,024⌋, 1,024] = [819, 1,024], mean (819 + 1,024) / 2 = 921.5 for prompts and outputs. A typical decoding sequence sits at context 921.5 + 921.5 / 2 = 1,382.25. Four users: **K = A = 4 × 1,382.25 = 5,529**, **T = 4**, **seqs = 4**.
2. **Memory.** kv·K = 163,840 × 5,529 = 905,871,360 B; + W 70,550,000,000 = 71,455,871,360 B; ÷ 4 = **17,863,967,840 B per GPU**. η_m·BW = 0.86 × 3.35e12 = 2.881e12 B/s, so **memS = 6.200614 ms**.
3. **Compute.** 2 × 70.55e9 × 4 = 564,400,000,000; 4 × 80 × 8,192 × 5,529 = 14,493,941,760; sum 578,893,941,760 ÷ 4 = **144,723,485,440 FLOP per GPU**. η_f·F = 0.50 × 1.979e15 = 9.895e14 FLOP/s, so **flopS = 0.146259 ms**. The max takes memory: **memory-bound**.
4. **Fixed.** 80 × 68.8 + 4 × 69.0 = 5,504 + 276 = 5,780 µs, so **fixedS = 5.780000 ms**.
5. **Link.** 2 × 80 × 4 × 8,192 × 2 × 2 × 3 ÷ 4 = **15,728,640 B**; ÷ 231e9 B/s = **linkS = 0.068089 ms**.
6. **Step.** 5.780000 + 0.068089 + 6.200614 = 12.048703 ms → **us = 12,049**. Against 11.776 ms measured: **+2.3 %**. (The prototype engine's mean TPOT, which includes the prefill steps of replacement requests, is 12.18 ms, +3.4 %; leave-one-out +3.6 % [proto].)
7. **What the debrief shows** (H4 labels; no split taught as fact): napkin max(17,863,967,840 ÷ 3.35e12, 144,723,485,440 ÷ 1.979e15) = **5.33 ms (−54.7 %)**; card **12.05 ms**; measured **11.78 ms**; v1 **50 ms (+324.6 %)**. The measured-only finding is safe to state: at c = 4, 1k/1k, TP 2 → TP 8 is 4.0× on the napkin and 17.41 → 9.11 ms = **1.91× measured** (ids 42017, 41625). "Something per step does not divide by TP" is the lesson; how much of it is fixed cost is this fit's split.

### 3.7 Worked example B: a prefill step (B200 · FP8, TP 1, 4 users, ~8k prompts, ~1k outputs)

**Published.** InferenceX id **40518**, raw member `"median_ttft":0.654017546446994`, so **654.02 ms**; run https://github.com/SemiAnalysisAI/InferenceX/actions/runs/18924487526/attempts/3. Parameters: the all-points prototype values η_m 0.84, η_f 0.44, t_layer 61.1 µs, t_seq 34.6 µs, harness 52.7 ms [proto].

2. **Load.** T = 7,373 + 3 = **7,376**; K = 7,373 + 3 × 7,834 = **30,875**; A = 7,373 × 7,374 / 2 + 3 × 7,834 = 27,184,251 + 23,502 = **27,207,753**; seqs = **4**.
3. **Compute.** 2 × 70.55e9 × 7,376 = 1,040,753,600,000,000; 4 × 80 × 8,192 × 27,207,753 = 71,323,492,024,320; sum **1,112,077,092,024,320 FLOP**. η_f·F = 0.44 × 4.5e15 = 1.98e15, so **flopS = 561.655097 ms**.
4. **Memory.** 70.55e9 + 163,840 × 30,875 (5,058,560,000) = 75,608,560,000 B ÷ (0.84 × 8e12 = 6.72e12) = **memS = 11.251274 ms**. **Compute-bound.**
5. **Fixed.** 80 × 61.1 + 4 × 34.6 = 4,888 + 138.4 = 5,026.4 µs, **fixedS = 5.026400 ms**. **Link:** 0 (TP 1).
6. **Step.** 5.026400 + 0 + 561.655097 = 566.681497 ms → **us = 566,681**. That is `EngineV2`'s TTFT for this request: admitted at a step boundary, first token stamped at the end of the step that completes its prefill.
7. **Against the published TTFT.** The published figure is client-side, so the comparison adds the row's harness term, which lives outside the engine (S5-D11): 566.681 + 52.7 = **619.38 ms** against 654.02 measured, **−5.3 %**. The card alone is **−13.4 %**. (Prototype engine median 628.5 ms, −3.9 %; leave-one-out −7.6 % [proto].)
8. **Debrief.** Napkin 1,112,077,092,024,320 ÷ 4.5e15 = **247.13 ms (−62.2 %)** (compute-bound at η = 1 too); card + harness **619 ms**; measured **654 ms**; v1 ⌈7,373 / 128⌉ − 1 = 57 ticks × 50 ms = **2,850 ms**, with no compute ceiling at all.

### 3.8 The two-card interference rule (the `frontier` reader uses it)

A long prompt arriving among c running users makes one step of about t_pre instead of t_dec, and each user's roughly OSL decode steps include about (c − 1) such steps:

TPOT ≈ t_dec + (c − 1)(t_pre − t_dec) ÷ OSL.

Checked on measured points [proto]: H100 TP 4, c = 64, 8k/1k: 24.27 + 63 × 395.6 ÷ 921.5 = **51.3 ms** against 53.49 measured (id 42004); B200 TP 1, c = 4: 18.08 against 18.34 (id 40518).

### 5.3 Replay and fit (S5-06; Opus first)

1. **Load and check.** Read the extract and check its sha256 against the dataset claim. Select and filter per the protocol, printing each drop and its reason; the dropped ids must equal `expectDropped`.
2. **Replay.** For each kept point (F ∪ H), run `EngineV2` with `closedLoop({conc: c, n: 10·c, isl, osl, ratio: 0.8, seed: hash32('ix:' + id)})` (lengths uniform on integers [⌊0.8·L⌋, L], all requests queued at t = 0 in id order), `maxNumSeqs = c`, `batchTokens` = 8,192, `blockSize` = 16, `numBlocks = ⌊(0.9 · HBM · TP − W) ÷ (kv · 16)⌋`, and a **recording** card that logs each step's `(tokens, kvTokens, attnPairs, seqs)` and which requests decoded or completed prefill in it. The loop is closed and `ignore_eos` fixes the lengths, so the step schedule does not depend on durations: one replay per point serves every parameter set (S5-D9).
3. **Observation weights.** Mean TPOT is the mean over requests of `(lastUs − firstUs) / (osl_r − 1)`: a weighted sum of step durations with weight `Σ_{r decoding in s} 1 / ((osl_r − 1) · R)` per step s. Median TTFT is the median request's admission-to-first-token window, the sum of that request's steps. A prediction is Σ_s w_s · stepS_s(θ); TTFT adds the harness term only when compared with the published value.
4. **Fit** (`fit.ts`, pure, numeric-linted, fixed order). For each η_m on the grid (S5-D35) at the current η_f, (t_layer, t_seq, 1/β) come from non-negative least squares on relative TPOT error, enumerating every active set; the best η_m wins. Start at η_f = 0.60; then three rounds of: (a) for each η_f on the grid, the harness term in closed form (weighted least squares, clipped at 0) and the TTFT error over every fit point's median TTFT, keeping the best η_f; (b) the TPOT fit again at that η_f. The max inside each step is taken per step, so no closed form is assumed; the reported memory-bound share is per point.
5. **LOO** over F: refit without each point (the whole procedure above), then predict its TPOT, and its TTFT if its ISL is 8,192. **Held-out:** the F fit predicts every H point.
6. **LOTPO and LOSO** (printed): refit without all points of one TP (or one shape) and predict them.
7. **Statistics:** error |pred / meas − 1|; mean arithmetic; p90 the nearest rank `sorted[⌈0.9·n⌉ − 1]` (v1's `p95` convention, `fleet-model.ts:447-448`); max the largest.

### 5.5 Leave-one-out, exactly

For a row with fit set F (n points), each i ∈ F is predicted by a full refit (grid, NNLS and the TTFT alternation) on F \ {i}, using the same replay logs. The held-out point's own log is used only for its prediction. No parameter, bound or grid choice is re-tuned after S5-00.

### 5.6 Consistency check

On 3 configurations per row (the row's smallest TP at c 4 1k/1k, its largest TP at c 64 1k/1k, and its smallest TP at c 4 8k/1k), `EngineV2` runs with the written table and a real clock, not the recorder. Its mean TPOT and median TTFT must equal the weighted-sum prediction to within 1 µs per step, summed over the run. It runs in fast mode, in a few seconds, and proves that the numbers the gate scored are the numbers the engine produces. If it cannot be met, stop before the verdict (§9.4).

### 5.7 What a failing row does

- **It stays visible:** in `table.ts` with `status: 'failed'` and its numbers (an explicit generated diff, never silent), and on the tab with its gate table.
- **The engine refuses it:** `EngineV2` throws `NotCalibrated(row, metric)` in calibrated mode.
- **Its consumers are unregistered:** a v2 exercise def or calibrated `step` variant naming the row fails `verify:physics` until it drops the row.
- **The decision** (S5-07's PR body states it):
  - **Both FP8 rows fail:** S5 closes with its default (§9.3). Level 1 ships; Level 2 is cancelled; the Device Mesh and the Throughput Factory stay gated. A retry needs a newer same-date H100 + B200 sweep, a protocol amendment and a new physics id.
  - **One FP8 row fails:** v2 runs on the other only; `frontier`'s classes shrink to that row and its fairness is re-measured (§7.1's kill rules).
  - **NVFP4 fails:** `step/quant-speedup` and the FP8 → NVFP4 finding drop.
- **On a later refresh** (TTL lapse, a claim change) `verify:physics` fails the refreshing PR; the integrator keeps the old claims (shown "stale since") or closes the row. Stored exercise outcomes are history and are never re-derived.

### 6.2 `EngineV2` (S5-05; Opus first)

```ts
// src/lib/world/physics/engine-v2.ts
export const ENGINE_V2_REV = 'ev2-1'           // bumped with any change to scheduling or stamping semantics
export class NotCalibrated extends Error { constructor(readonly row: string, readonly metric: 'tpot' | 'ttft') }
export class OutOfBox extends Error { constructor(readonly row: string, readonly reason: string) }
export interface EngineV2Config {
  physics: { id: string; row: CalibratedRow; tp: number }   // id = PHYS_ID
  maxNumSeqs: number            // vLLM max_num_seqs semantics
  batchTokens: number           // per-step token budget (box: 8,192)
  blockSize: 16
  numBlocks?: number            // default ⌊(0.9·HBM·TP − W) ÷ (kv·16)⌋
  metric?: 'tpot' | 'ttft'      // what the caller will read; checked against the row's eligibility (default 'tpot')
  explore?: boolean             // allow failed rows and out-of-box configurations, labelled; never graded
}
export interface FinishedV2 { id: number; arrivalUs: number; admitUs: number; firstUs: number; lastUs: number;
  ttftUs: number /* from arrival */; ttftAdmitUs: number; tpotUs: number; queueUs: number }
export class EngineV2 {
  constructor(cfg: EngineV2Config, mgr: ManagerDriver /* RefBlockManager */, client: ClientDriver)
  step(): void                  // exactly one iteration (or an idle jump, which is not one)
  done(): boolean
  readonly clockUs: number      // integer µs
  readonly iterations: number
  readonly outOfEnvelope: number
  lastCard?: StepCard
  onFinish?: (r: FinishedV2) => void
  stats(): EngineV2Stats        // µs: mean TPOT, median TTFT (admission), tok/s/user, output tok/s/GPU, iterations, outOfEnvelope
}
```

- **Step order.**
  1. If nothing is running or waiting, set `clockUs` to the next arrival: no step, no iteration.
  2. Inject due arrivals (`arrivalUs ≤ clockUs`).
  3. Admit waiting requests FCFS while `running < maxNumSeqs` and the block manager allocates the prompt's blocks.
  4. Form the batch: decodes first (one token each), then running prefills continue their chunk, then newly admitted prefills, in arrival order, each taking `min(left, budgetLeft)`.
  5. Build `StepLoad` (§3.1); `card = stepCard(row.spec, tp, load)`.
  6. `clockUs += card.us`.
  7. Stamp at the new `clockUs`: a prefill that completes → `firstUs`; a decode → `lastUs`; a completion → `tpotUs = (lastUs − firstUs) / (output − 1)`, and its blocks free.
  8. `outOfEnvelope += exceeds(envelope, load, tp) ? 1 : 0`; `iterations++`.
- **Preemption** is recompute, newest first (`production.vllm.v1-preemption`). In-box runs never preempt, by the box's KV rule; a test asserts it on every replay.
- **Validation.** `NotCalibrated` on a failed row or an ineligible metric and `OutOfBox` on an out-of-box configuration, unless `explore`. No faults, no cluster, no scheduler plug-in (S5-D26). Imports from `fleet-model.ts`: types and `RefBlockManager` only.
- **Client** (`client.ts`). `closedLoop({conc, n, isl, osl, ratio, seed})`: n requests with lengths drawn uniformly on the integers [⌊ratio·L⌋, L] from a `src/lib/rng.ts` stream seeded by `seed`, all with `arrivalUs = 0`, ids 0 … n − 1 in draw order. `openLoop({ratePerS, n, seed})` (built and tested, unused in S5): arrivals on the 50 ms grid, `arrivalUs = tick × 50,000`.

### 6.3 Box and envelope

- **Box** (per row, in `table.ts`; `inBox(row, cfg)` returns `{ok, reason}`): the Llama-3-70B architecture; FP8 weights (NVFP4 on that row) with FP8 KV; `tp ∈ boxTp`; `maxNumSeqs ≤ 64`; shape ∈ {1k/1k, 1k/8k, 8k/1k} nominal at range ratio 0.8; `batchTokens = 8,192`; prefix caching off; `c·(isl + osl)` ≤ the KV room of §4.1.
- **Envelope** (per row, from the replay logs of F ∪ H): the maximum per step of `tokens`, decoding sequences, `kvTokens / tp` and `attnPairs / tp`. A step above any of them increments `outOfEnvelope`; an exercise band rejects any seed with `outOfEnvelope > 0`.

## 7. The exercises, their honesty and their fairness

### 7.0 Honesty and fairness rules (they bind every graded v2 answer)

- **H1, decision-level.** A graded quantity Q (an argmax, a ratio, a level) is validated as Q itself on published configurations, each side predicted by a leave-one-out refit, with the protocol's `h1` rules: tolerance (numeric Q) ≥ max(15 %, the p90 of Q's LOO error), rounded up to a whole percent; separation (choice Q): the measured winner beats the runner-up by ≥ 1 / (1 − δ_sep), δ_sep the p90 of the LOO error of the winner-to-runner-up ratio over the row's published option pairs; membership: every option is ≥ δ_mem (the row's TPOT LOO p90) from its threshold; LOO agreement: the answer from LOO predictions equals the answer from measured values. The tables are generated in `docs/physics/decisions.json` (S5-08).
- **H2, measured agreement.** Where every option is a published point, the engine's answer equals the answer from InferenceX's measured values (`IX_INBOX`); otherwise the seed is out of band.
- **H3, box and envelope.** Graded and unlabelled only in box; any out-of-envelope step makes the seed out of band.
- **H4, labels.** Every v2 number carries `[v2 physics · <chip> · vLLM 0.10.2 · <precision> · fitted on <n_F> InferenceX points (2025-10-29) · 9 in 10 within <G1 p90>% (leave-one-out) · <PHYS_ID>]`, with claim chips (the dataset claim, the row's `phys.*` claims) that open the tab. Parameters read "this fit's numbers". [proto] example: `[v2 physics · H100 SXM · vLLM 0.10.2 · FP8 · fitted on 25 InferenceX points (2025-10-29) · 9 in 10 within 11.3% (leave-one-out) · v2-…]`.
- **Fairness** (wave-3 D39, as D70 applies it): the scene is shown before the prediction; done = 3 right in a row on fresh seeds with ≥ 2 distinct answers; no answer right on more than about 29 % of banded seeds; the best scene-ignoring guesser (`ignoring()`, `tests/fleet-ex/done-rule.test.ts:92-111`) finishes within 10 rounds ≤ 14 % of the time (≤ 40 % within 30); a scene reader finishes within 10 rounds > 90 % of the time. For free numbers, the best constant's P(3 in a row within 10) has the same 14 % bound.

### 7.1 E1 · `frontier` (Fleet exercise on `EngineV2`; t7.l3; S5-13; ships only if every check passes in the repo)

- **Lesson.** t7.l3 Pareto (`src/data/lessons/t7/pareto.ts`, `exercise: 'read+quiz'`); KCs `t7.pareto-frontier`, `t7.frontier-shifts`. The lesson says "The frontier is concave" and that the curve's shape is physics; in v1 tok/s/user is 20 at every concurrency, so the frontier is a vertical line. This is the one learner question v1 makes impossible.
- **Scene (shown first).** A row (chip, engine release and precision as claims); a shape (~1k/~1k, ~1k/~8k or ~8k/~1k); a **floor** in tok/s per user (synthetic, labelled); the option grid, the row's box TPs × c ∈ {4, 16, 64}, with KV-excluded options shown as "won't fit: KV"; the row's card parameters as "the engine's numbers".
- **Prediction.** The option with the most output tok/s per GPU among those whose mean tok/s per user meets the floor; the answer is the point code `100·TP + c`.
- **Truth.** `frontier-sweep` runs the 3 closed-loop replays of the scene's shape (c = 4, 16, 64, seeded by the published point ids, memoised per shape in the worker), evaluates each option's mean TPOT through the row's card per TP, and takes the argmax of tok/s/GPU = c ÷ (TPOT × TP) among options with tok/s/user = 1 / TPOT ≥ floor.
- **Scene sampling (O12).** The seed draws a class uniformly from the committed gradeable classes in `frontier-scenes.json`, then a shape and a floor (0.1 tok/s/user steps) uniformly within that class's floor intervals. A class is a (row, answer) pair that passes measured H1 and LOO agreement on a floor interval at least 3 tok/s/user wide.
- **Band.** ≥ 2 options qualify; H1's margins hold on the engine's values as well as the measured ones; H2; no out-of-envelope step.
- **Pass.** Exact. **Debrief:** `StepCard` and the table for the winner and the runner-up (napkin, card, measured, `run_url`); the why: "per-GPU throughput rises with c until the floor bites; a bigger TP divides bytes but not the per-step fixed costs, so TP 8 rarely wins per GPU".
- **In-production rows** (S5-D39): `production.vllm.max-num-seqs`, `production.vllm.max-num-batched-tokens` (labelled as today's vLLM defaults, not the harness's settings), and `status.inferencex.harness.batch-tokens` and `.max-num-seqs` (pinned to the harness commit).
- **Fairness measured on the prototype** [proto]:

- **Reader check.** A scene reader applies §3.8's two-card rule to each option with the shown parameters; it must finish within 10 rounds > 90 % of the time on banded seeds (printed). ### 7.2 E2 · `step/decode-ms` (generator; t4.l3, t5.l3; KCs `t4.decode-bandwidth`, `t5.latency-metrics`)

### 7.3 E3 · `step/tp-speedup` (calibrated; S5-14; t6.l4; KC `t6.parallelism-composition`)

How much shorter a calibrated row's decode step gets from TP a to TP b at concurrency c, from the card with given parameters; exact to the family tolerance; the why shows the measured ratio for published configurations (c 4, 1k/1k, TP 2 → 8: 17.41 → 9.11 ms, 1.91×). **Not an engine exercise** [proto]: over 123 published pairs (measured 1.08–2.99×; ratio LOO p90 9.5 %) the best constant, 1.398, is within 15 % on 56 % of pairs, so P(3 in a row within 10) = 63 %, far above 14 %.

### 7.4 E4 · `step/quant-bytes` (η-free, S5-10) and `step/quant-speedup` (calibrated on B200 NVFP4 TP 1–4, S5-14); t6.l5; KC `t6.fp4-capacity`

`quant-bytes`: the weight-byte ratio between BF16, FP8 and NVFP4 (2, 1 and 0.5625 B per parameter; `serving.nvfp4.bits-per-weight`). `quant-speedup`: the card's FP8 → NVFP4 step ratio at a configuration. The why: 1.78× fewer bytes, but measured TPOT drops only 1.01–1.32× at TP 1–4 (43 pairs [proto]), because the fixed and per-sequence terms do not shrink. **Not an engine exercise** [proto]: the best constant, 1.157, is within 15 % on 100 % of pairs (ratio LOO p90 6.0 %).

### 7.5 Also η-free (S5-10): `step/prefill-ms` and `step/ridge-kv`

- **`prefill-ms`** (t5.l3; `t5.prefill-vs-decode`): P tokens × 2·params ÷ F plus the attention term, at η = 1. Its calibrated form (S5-14) ships only on TTFT-eligible rows.
- **`ridge-kv`** (t4.l3; `t4.ridge-point`): decode intensity with KV, 2·P·b ÷ (2P + b·ctx·kv), against the ridge. It tends to 2P ÷ (ctx·kv); for Llama-3-8B BF16 (P = 8.03e9, kv = 131,072 B) that is 16.06e9 ÷ (2,048 × 131,072) = **59.8 FLOP/B** at a 2k context and 239.3 at 512, against H100's BF16 ridge of 989 ÷ 3.35 = **295.2**, so decode at a 2k context is never compute-bound on an H100 at any batch.

## 10. Task DAG for Sonnet implementers

### 10.1 How the PRs fit together

- **One PR per task into its integration branch**, as in Waves 1–3. Each task works in its own worktree; its prompt names the base sha and checks it with `git merge-base --is-ancestor`, because worktrees start at `master`. Each worktree makes a private hard-linked `node_modules`. The integrator merges a level before the next starts and runs every gate on the merged tree.
