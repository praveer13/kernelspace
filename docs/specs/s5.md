## 0. Summary

In v1 the Fleet's clock is flat: one iteration is 50 ms whatever it carries (`SIM_TICK_SECONDS`, `fleet-model.ts:452`). Four lessons' central claims contradict it (t5.l3's "slower pace" item, t7.l3's concave frontier, t5.l8's chunk trade-off, t6.l5's "decode rates scale with it"), and Boot already runs an η = 1 step-time model that the Fleet ignores.

**S5 calibrates first and teaches second.**
- **The physics** is one hand-workable step card (§3): `step = layers·t_layer + seqs·t_seq + linkBytes ÷ β + max(memBytes ÷ (η_m·BW), FLOPs ÷ (η_f·F))`, rounded to integer µs. Model and hardware inputs are claims; five parameters per row are fitted. Only the card's predictions are validated, never its split into terms.
- **The engine** is a separate `EngineV2` under `src/lib/world/physics/`, so `fleet-model.ts` and every v1 pin stay byte-identical.
- **The gate** (`verify:physics`) replays every published point of one pinned InferenceX sweep (2025-10-29, vLLM 0.10.2) through `EngineV2`, fits each row on a declared subset and scores leave-one-out and held-out error against a protocol written before the fit runs.
- **The verdict** (S5-07) decides: rows that pass are calibrated; if both FP8 rows fail, S5 closes with its default.
- **The default ships whatever the gate says:** the η = 1 card pinned to Boot and the KV calculator, four η-free `step` generator variants, three errata, and a physics tab on `/freshness` that shows the gate's numbers, positive or negative.

## 3. The physics (S5-02)

### 3.1 What one step carries

A step is one engine iteration. Running sequences decode first, one token each. Prefill chunks then fill the rest of the step's token budget (the harness's 8,192, `status.inferencex.harness.batch-tokens`, S5-D34) in arrival order, up to `maxNumSeqs` sequences (vLLM V1 has "no prefill or decode phase", claim `twin.vllm.scheduler`). From the batch the card reads four integers:

| Field | Meaning | A decoding sequence at context c | A prefill chunk of p tokens after h already prefilled |
|---|---|---|---|
| `tokens` (T) | tokens computed this step | 1 | p |
| `kvTokens` (K) | KV entries read or written this step | c | h + p |
| `attnPairs` (A) | causal attention token pairs | c | p·h + p(p+1)/2 |
| `seqs` | sequences in the step | 1 | 1 |

Each field is summed over the batch. Every value stays below 2^53, so the sums are exact integers.

### 3.2 The card

```ts
// src/lib/world/physics/types.ts
export interface ChipShape { bwBps: number; peakFlops: number; hbmBytes: number }   // B/s, FLOP/s at the row's weight precision, bytes
export interface ModelShape { params: number; layers: number; hidden: number; kvBytesPerToken: number; weightBytes: number }
export interface CardParams { etaMem: number; etaFlop: number; layerUs: number; seqUs: number; linkGBs: number | null } // null: no link term
export interface CardSpec { chip: ChipShape; model: ModelShape; params: CardParams }
export interface StepLoad { seqs: number; tokens: number; kvTokens: number; attnPairs: number }
export interface StepCard {
  memBytes: number; flops: number; linkBytes: number      // per GPU
  memS: number; flopS: number; fixedS: number; linkS: number; stepS: number
  bound: 'mem' | 'flop'
  us: number                                               // the step's duration, integer µs
}
// src/lib/world/physics/card.ts
export const NAPKIN: CardParams = { etaMem: 1, etaFlop: 1, layerUs: 0, seqUs: 0, linkGBs: null }  // "the datasheet bound"
export function stepCard(spec: CardSpec, tp: number, load: StepLoad): StepCard
```

The operation order is part of the contract (the golden step vectors pin it):

```
memBytes  = (W + kv·K) / tp                                   W = model.weightBytes, kv = model.kvBytesPerToken
flops     = (2·params·T + 4·layers·hidden·A) / tp
linkBytes = tp > 1 ? (2·layers·T·hidden·2·2·(tp − 1)) / tp : 0   two ring all-reduces of BF16 activations per layer
memS      = memBytes / (etaMem · bwBps)
flopS     = flops / (etaFlop · peakFlops)
linkS     = linkGBs === null || tp === 1 ? 0 : linkBytes / (linkGBs · 1e9)
fixedS    = (layers · layerUs + seqs · seqUs) / 1e6
stepS     = fixedS + linkS + Math.max(memS, flopS)
us        = Math.round(stepS · 1e6)                           bound = memS ≥ flopS ? 'mem' : 'flop'
```

- `ChipShape` and `ModelShape` are built from claims with `claimNumber(id, scale)` exactly as Boot builds its inputs (`claimNumber(id, 1e12)` for TB/s and TFLOP/s, `1e9` for GB and B params; `src/lib/boot/model.ts`, `bootInputs`). The engine never calls `claimNumber` (I3): `table.ts` stores the built shapes.
- The engine's step duration is exactly `card.us`. `EngineV2` keeps the last card (`lastCard`), so a panel can print the step it ran.
- **The napkin pin (S5-D38).** With `NAPKIN`, tp 1, T = 1, K = Boot's `chats × CHAT_TOKENS`, Boot's own chip and model (BF16 Llama-3-8B, 2 B per weight), `memS` === `deriveBoot().stepSeconds`, and with K = 0 `memS` === `tokenSeconds`. `kv.ts`'s `itlMs` (its fixtures) agrees to 1e-12 relative. `roofline` `decode-b1` is a rate in tok/s scaled by a drawn bandwidth fraction `fb`: on instances with `fb` = 100, 1 ÷ `memS` (K = 0, W = paramsB·1e9·bytes(dtype), the same chip) equals the truth to 1e-12 relative; `fb` < 100 is out of scope. No caller changes.

### 3.6 Worked example A: a decode step (H100 · FP8, TP 4, 4 users, ~1k prompts, ~1k outputs)

**Published.** InferenceX id **41187**, raw member `"mean_tpot":0.011776147370379336`, so **11.776 ms**; run https://github.com/SemiAnalysisAI/InferenceX/actions/runs/18924448230/attempts/2; pinned query in §4.1. The parameters are the all-points prototype values (η_m 0.86, η_f 0.50, t_layer 68.8 µs, t_seq 69.0 µs, β 231 GB/s) [proto]. Re-derived for this spec in the operation order of §3.2:

1. **Lengths.** The harness draws lengths uniformly on the integers [⌊0.8 × 1,024⌋, 1,024] = [819, 1,024], mean (819 + 1,024) / 2 = 921.5 for prompts and outputs. A typical decoding sequence sits at context 921.5 + 921.5 / 2 = 1,382.25. Four users: **K = A = 4 × 1,382.25 = 5,529**, **T = 4**, **seqs = 4**.
2. **Memory.** kv·K = 163,840 × 5,529 = 905,871,360 B; + W 70,550,000,000 = 71,455,871,360 B; ÷ 4 = **17,863,967,840 B per GPU**. η_m·BW = 0.86 × 3.35e12 = 2.881e12 B/s, so **memS = 6.200614 ms**.
3. **Compute.** 2 × 70.55e9 × 4 = 564,400,000,000; 4 × 80 × 8,192 × 5,529 = 14,493,941,760; sum 578,893,941,760 ÷ 4 = **144,723,485,440 FLOP per GPU**. η_f·F = 0.50 × 1.979e15 = 9.895e14 FLOP/s, so **flopS = 0.146259 ms**. The max takes memory: **memory-bound**.
4. **Fixed.** 80 × 68.8 + 4 × 69.0 = 5,504 + 276 = 5,780 µs, so **fixedS = 5.780000 ms**.
5. **Link.** 2 × 80 × 4 × 8,192 × 2 × 2 × 3 ÷ 4 = **15,728,640 B**; ÷ 231e9 B/s = **linkS = 0.068089 ms**.
6. **Step.** 5.780000 + 0.068089 + 6.200614 = 12.048703 ms → **us = 12,049**. Against 11.776 ms measured: **+2.3 %**. (The prototype engine's mean TPOT, which includes the prefill steps of replacement requests, is 12.18 ms, +3.4 %; leave-one-out +3.6 % [proto].)

The measured-only finding is safe to state: at c = 4, 1k/1k, TP 2 → TP 8 is 4.0× on the napkin and 17.41 → 9.11 ms = **1.91× measured** (ids 42017, 41625). "Something per step does not divide by TP" is the lesson; how much of it is fixed cost is this fit's split.

### 3.7 Worked example B: a prefill step (B200 · FP8, TP 1, 4 users, ~8k prompts, ~1k outputs)

**Published.** InferenceX id **40518**, raw member `"median_ttft":0.654017546446994`, so **654.02 ms**; run https://github.com/SemiAnalysisAI/InferenceX/actions/runs/18924487526/attempts/3. 2. **Load.** T = 7,373 + 3 = **7,376**; K = 7,373 + 3 × 7,834 = **30,875**; A = 7,373 × 7,374 / 2 + 3 × 7,834 = 27,184,251 + 23,502 = **27,207,753**; seqs = **4**.

5. **Fixed.** 80 × 61.1 + 4 × 34.6 = 4,888 + 138.4 = 5,026.4 µs, **fixedS = 5.026400 ms**. **Link:** 0 (TP 1).
6. **Step.** 5.026400 + 0 + 561.655097 = 566.681497 ms → **us = 566,681**. That is `EngineV2`'s TTFT for this request: admitted at a step boundary, first token stamped at the end of the step that completes its prefill.

### 3.8 The two-card interference rule (the `frontier` reader uses it)

A long prompt arriving among c running users makes one step of about t_pre instead of t_dec, and each user's roughly OSL decode steps include about (c − 1) such steps:

TPOT ≈ t_dec + (c − 1)(t_pre − t_dec) ÷ OSL.

Checked on measured points [proto]: H100 TP 4, c = 64, 8k/1k: 24.27 + 63 × 395.6 ÷ 921.5 = **51.3 ms** against 53.49 measured (id 42004); B200 TP 1, c = 4: 18.08 against 18.34 (id 40518).

### 5.3 Replay and fit (S5-06; Opus first)

1. **Load and check.** Read the extract and check its sha256 against the dataset claim. Select and filter per the protocol (W and kv from the model byte claims), printing each drop and its reason; the dropped ids must equal `expectDropped`, and S5-06's test asserts the kept 42/58/60 and F/H 25/17, 34/24, 36/24 (S5-D52).
2. **Replay.** For each kept point (F ∪ H), run `EngineV2` with `closedLoop({conc: c, n: 10·c, isl, osl, ratio: 0.8, seed: hash32('ix:' + id)})` (lengths uniform on integers [⌊0.8·L⌋, L], all requests queued at t = 0 in id order), `maxNumSeqs = c`, `batchTokens` = 8,192, `blockSize` = 16, `numBlocks = ⌊(0.9 · HBM · TP − W) ÷ (kv · 16)⌋`, recording through `EngineV2`'s `onStep` hook with a `card` override (S5-D53): each step's `(tokens, kvTokens, attnPairs, seqs)` and which requests decoded, completed prefill or were admitted in it. The loop is closed and `ignore_eos` fixes the lengths, so the step schedule does not depend on durations: one replay per point serves every parameter set (S5-D9).
3. **Observation weights.** Mean TPOT is the mean over requests of `(lastUs − firstUs) / (osl_r − 1)`: a weighted sum of step durations with weight `Σ_{r decoding in s} 1 / ((osl_r − 1) · R)` per step s. A TPOT prediction is Σ_s w_s · stepS_s(θ) with these fixed weights. Median TTFT is not a fixed-weight sum: each request's admission-to-first-token window (the sum of its steps' stepS_s(θ)) is computed per parameter set θ, and the median is then taken over requests by the protocol's rule (n = 10·c is even, so the mean of the two middle values, as the harness's `np.median`); which requests sit in the middle can change with θ. TTFT adds the harness term only when compared with the published value.
4. **Fit** (`fit.ts`, pure, numeric-linted, fixed order). For each η_m on the grid (S5-D35) at the current η_f, (t_layer, t_seq, 1/β) come from non-negative least squares on relative TPOT error, enumerating every active set; the best η_m wins. Start at η_f = 0.60; then three rounds of: (a) for each η_f on the grid, the harness term in closed form (weighted least squares, clipped at 0) and the TTFT error over every fit point's median TTFT, keeping the best η_f; (b) the TPOT fit again at that η_f. The max inside each step is taken per step, so no closed form is assumed; the reported memory-bound share is per point. Each point's weighted kernel Σ_s w_s · max(memS_s, flopS_s) depends only on (η_m, η_f), so it is memoised per row and shared by the fit and every LOO, LOTPO and LOSO refit (protocol `fit.memo`); without it LOO costs about n_F times more and `--full` misses its 120 s.
5. **LOO** over F: refit without each point (the whole procedure above), then predict its TPOT, and its TTFT if its ISL is 8,192. **Held-out:** the F fit predicts every H point.
6. **LOTPO and LOSO** (printed): refit without all points of one TP (or one shape) and predict them.
7. **Statistics:** error |pred / meas − 1|; mean arithmetic; p90 the nearest rank `sorted[⌈0.9·n⌉ − 1]` (v1's `p95` convention, `fleet-model.ts:447-448`); max the largest; median the mean of the two middle values for even n, the middle one for odd (the protocol's `stats.median`; `EngineV2.stats()` uses the same rule).

### 5.5 Leave-one-out, exactly

For a row with fit set F (n points), each i ∈ F is predicted by a full refit (grid, NNLS and the TTFT alternation) on F \ {i}, using the same replay logs. The held-out point's own log is used only for its prediction. No parameter, bound or grid choice is re-tuned after S5-00.

### 5.6 Consistency check

On 3 configurations per row (the row's smallest TP at c 4 1k/1k, its largest TP at c 64 1k/1k, and its smallest TP at c 4 8k/1k), `EngineV2` runs with the written table and a real clock, not the recorder. Its mean TPOT and median TTFT must equal the weighted-sum prediction (summed in float `stepS`, as the fit does) within the rounding the engine's integer-µs steps introduce: |Δ mean TPOT| ≤ 0.5 µs (a request's TPOT averages its osl − 1 rounded steps), and |Δ median TTFT| ≤ 0.5 µs × the number of steps in the median windows (protocol `consistency`). It runs in fast mode, in a few seconds, and proves that the numbers the gate scored are the numbers the engine produces. If it cannot be met, stop before the verdict (§9.4).

### 5.7 What a failing row does

- **It stays visible:** in `table.ts` with `status: 'failed'` and its numbers (an explicit generated diff, never silent), and on the tab with its gate table.
- **The engine refuses it:** `EngineV2` throws `NotCalibrated(row, metric)` in calibrated mode.
- **Its consumers are unregistered:** a v2 exercise def or calibrated `step` variant naming the row fails `verify:physics` (through the consumer contract, §5.2) until it drops the row.
- **The decision** (S5-07's PR body states it):
  - **Both FP8 rows fail:** S5 closes with its default (§9.3). Level 1 ships; Level 2 is cancelled; the Device Mesh and the Throughput Factory stay gated. A retry needs a newer same-date H100 + B200 sweep, a protocol amendment and a new physics id.
  - **One FP8 row fails:** v2 runs on the other only; `frontier`'s classes shrink to that row and its fairness is re-measured (§7.1's kill rules).
  - **NVFP4 fails:** `step/quant-speedup` and the FP8 → NVFP4 finding drop.
- **On a later refresh** (TTL lapse, a claim change) `verify:physics` fails the refreshing PR; the integrator keeps the old claims (shown "stale since") or closes the row. Stored exercise outcomes are history and are never re-derived.

### 6.2 `EngineV2` (S5-05; Opus first)

```ts
// src/lib/world/physics/engine-v2.ts
export const ENGINE_V2_REV = 'ev2-1'           // bumped with any change to scheduling or stamping semantics
export class NotCalibrated extends Error { constructor(readonly row: string, readonly metric: 'tpot' | 'ttft') }
export class OutOfBox extends Error { constructor(readonly row: string, readonly reason: string) }
export interface EngineV2Config {
  physics: { id: string; row: CalibratedRow; tp: number }   // id = PHYS_ID
  maxNumSeqs: number            // vLLM max_num_seqs semantics
  batchTokens: number           // per-step token budget (box: 8,192)
  blockSize: 16
  numBlocks?: number            // default ⌊(0.9·HBM·TP − W) ÷ (kv·16)⌋
  metric?: 'tpot' | 'ttft'      // what the caller will read; checked against the row's eligibility (default 'tpot')
  explore?: boolean             // allow failed rows and out-of-box configurations, labelled; never graded
  onStep?: (s: StepRecord) => void   // called after step 4, before clockUs advances; unset: no effect (S5-D53)
  card?: (load: StepLoad, tp: number) => StepCard  // replaces stepCard for replays; only with explore (S5-D53)
}
export interface StepRecord { load: StepLoad; tp: number; decoded: readonly number[]; prefillDone: readonly number[]; admitted: readonly number[] }
export interface FinishedV2 { id: number; arrivalUs: number; admitUs: number; firstUs: number; lastUs: number;
  ttftUs: number /* from arrival */; ttftAdmitUs: number; tpotUs: number; queueUs: number }
export class EngineV2 {
  constructor(cfg: EngineV2Config, mgr: ManagerDriver /* callers build it with makeRefManager(numBlocks, 16) */, client: ClientDriver)
  step(): void                  // exactly one iteration (or an idle jump, which is not one)
  done(): boolean
  readonly clockUs: number      // integer µs
  readonly iterations: number
  readonly outOfEnvelope: number
  lastCard?: StepCard
  onFinish?: (r: FinishedV2) => void
  stats(): EngineV2Stats        // µs: mean TPOT, median TTFT (admission; protocol's median rule), tok/s/user, output tok/s/GPU, iterations, outOfEnvelope
}
// src/lib/world/physics/client.ts
export interface ClientDriver {
  nextArrivalUs(): number | null          // the next not-yet-injected arrival, or null when none is left
  due(clockUs: number): Request[]         // requests with arrivalUs ≤ clockUs not yet injected, in (arrivalUs, id) order
}
```

- **Step order.**
  1. If nothing is running or waiting, set `clockUs` to the next arrival: no step, no iteration.
  2. Inject due arrivals (`arrivalUs ≤ clockUs`).
  3. Admit waiting requests FCFS while `running < maxNumSeqs` and the block manager allocates the prompt's blocks.
  4. Form the batch: decodes first (one token each), then running prefills continue their chunk, then newly admitted prefills, in arrival order, each taking `min(left, budgetLeft)`.
  5. Build `StepLoad` (§3.1); call `onStep` if set; `card = cfg.card ? cfg.card(load, tp) : stepCard(row.spec, tp, load)`.
  6. `clockUs += card.us`.
  7. Stamp at the new `clockUs`: a prefill that completes → `firstUs`; a decode → `lastUs`; a completion → `tpotUs = (lastUs − firstUs) / (output − 1)`, and its blocks free.
  8. `outOfEnvelope += exceeds(envelope, load, tp) ? 1 : 0`; `iterations++`.
- **Preemption** is recompute, newest first (`production.vllm.v1-preemption`). In-box runs never preempt, by the box's KV rule; a test asserts it on every replay.
- **Validation.** `NotCalibrated` on a failed row or an ineligible metric and `OutOfBox` on an out-of-box configuration, unless `explore`. No faults, no cluster, no scheduler plug-in (S5-D26). Imports from `fleet-model.ts`: types (`ManagerDriver` among them) and `RefBlockManager` only; callers and tests build the driver with `makeRefManager(numBlocks, 16)` (`fleet-model.ts:352`).
- **Client** (`client.ts`). Both builders return a `ClientDriver`. `closedLoop({conc, n, isl, osl, ratio, seed})`: n requests with lengths drawn uniformly on the integers [⌊ratio·L⌋, L] from a `src/lib/rng.ts` stream seeded by `seed`, all with `arrivalUs = 0`, ids 0 … n − 1 in draw order. `openLoop({ratePerS, n, seed})` (built and tested, unused in S5): arrivals on the 50 ms grid, `arrivalUs = tick × 50,000`.

### 6.3 Box and envelope

- **Box** (per row, in `table.ts`; `inBox(row, cfg)` returns `{ok, reason}`): the Llama-3-70B architecture; FP8 weights (NVFP4 on that row) with FP8 KV; `tp ∈ boxTp`; `maxNumSeqs ≤ 64`; shape ∈ {1k/1k, 1k/8k, 8k/1k} nominal at range ratio 0.8; `batchTokens = 8,192`; prefix caching off; `c·(isl + osl)` ≤ the KV room of §4.1.
- **Envelope** (per row, from the replay logs of F ∪ H): the maximum per step of `tokens`, decoding sequences, `kvTokens / tp` and `attnPairs / tp`. A step above any of them increments `outOfEnvelope`; an exercise band rejects any seed with `outOfEnvelope > 0`.

## 7. The exercises, their honesty and their fairness

### 7.0 Honesty and fairness rules (H1 binds decisions graded against measured values; every v2 number carries H4)

- **H1, decision-level.** A graded quantity Q (an argmax, a ratio, a level) is validated as Q itself on published configurations, each side predicted by a leave-one-out refit, with the protocol's `h1` rules: tolerance (numeric Q) ≥ max(15 %, the p90 of Q's LOO error), rounded up to a whole percent; separation (choice Q): the measured winner beats the runner-up by ≥ 1 / (1 − δ_sep), δ_sep the p90 of the LOO error of the winner-to-runner-up ratio over the row's published option pairs; membership: every option is ≥ δ_mem (the row's TPOT LOO p90) from its threshold; LOO agreement: the answer from LOO predictions equals the answer from measured values. The tables are generated in `docs/physics/decisions.json` (S5-08). **Scope (S5-D57):** H1 governs decisions graded against reality, which in S5 is `frontier` alone; a `step` item grades the card's arithmetic with the parameters its stem gives, at the family tolerance (2 % relative), and carries H4 labels only.
- **H2, measured agreement.** Where every option is a published point, the engine's answer equals the answer from InferenceX's measured values (`IX_INBOX`); otherwise the seed is out of band.
- **H3, box and envelope.** Graded and unlabelled only in box; any out-of-envelope step makes the seed out of band.
- **H4, labels, per metric (S5-D58).** Every v2 number carries `[v2 physics · <chip> · vLLM 0.10.2 · <precision> · fitted on <n> InferenceX points (2025-10-29) · 9 in 10 within <p90>% (leave-one-out) · <PHYS_ID>]`, where n and p90 are the item's metric's: TPOT's G1 p90 and n_F for decode times, TTFT's 8k LOO p90 and its n (with the note "plus the harness term") for TTFT-derived numbers; a ratio prints no "9 in 10" clause. A test checks each label's metric. Labels carry claim chips (the dataset claim, the row's `phys.*` claims) that open the tab. Parameters read "this fit's numbers". [proto] example: `[v2 physics · H100 SXM · vLLM 0.10.2 · FP8 · fitted on 25 InferenceX points (2025-10-29) · 9 in 10 within 11.3% (leave-one-out) · v2-…]`.
- **Fairness** (wave-3 D39, as D70 applies it): the scene is shown before the prediction; done = 3 right in a row on fresh seeds with ≥ 2 distinct answers; no answer right on more than about 29 % of banded seeds; the best scene-ignoring guesser (`ignoring()`, `tests/fleet-ex/done-rule.test.ts:92-111`) finishes within 10 rounds ≤ 14 % of the time (≤ 40 % within 30); a scene reader finishes within 10 rounds > 90 % of the time. For free numbers, the best constant's P(3 in a row within 10) has the same 14 % bound. For `step` items (protocol `items`): over 2,000 instances the best constant is within the family tolerance on ≤ 10 %, and absolute answers span ≥ 10×; ratio variants have no span bound, only the constant-cover bound (`items.ratioRule`, S5-D57).

### 7.1 E1 · `frontier` (Fleet exercise on `EngineV2`; t7.l3; S5-13; ships only if every check passes in the repo)

- **Lesson.** t7.l3 Pareto (`src/data/lessons/t7/pareto.ts`, `exercise: 'read+quiz'`); KCs `t7.pareto-frontier`, `t7.frontier-shifts`. The lesson says "The frontier is concave" and that the curve's shape is physics; in v1 tok/s/user is 20 at every concurrency, so the frontier is a vertical line. This is the one learner question v1 makes impossible.
- **Scene (shown first).** A row (chip, engine release and precision as claims); a shape (~1k/~1k, ~1k/~8k or ~8k/~1k); a **floor** in tok/s per user (synthetic, labelled); the option grid, the row's box TPs × c ∈ {4, 16, 64}, with KV-excluded options shown as "won't fit: KV"; the row's card parameters as "the engine's numbers".
- **Prediction.** The option with the most output tok/s per GPU among those whose mean tok/s per user meets the floor; the answer is the point code `100·TP + c`.
- **Truth.** `frontier-sweep` runs the 3 closed-loop replays of the scene's shape (c = 4, 16, 64), one per (shape, c), seeded by the protocol's `frontier.replaySeed` = `hash32('ix-frontier:' + isl + '/' + osl + ':' + c)`, shared across TPs and rows and memoised per shape in the worker (S5-D60; the schedule does not depend on TP or row because in-box options never preempt); it records through `EngineV2`'s `onStep` hook, evaluates each option's mean TPOT through the row's card per TP, and takes the argmax of tok/s/GPU = c ÷ (TPOT × TP) among options with tok/s/user = 1 / TPOT ≥ floor.
- **Scene sampling (O12).** The seed draws a class uniformly from the committed gradeable classes in `frontier-scenes.json`, then a shape and a floor (0.1 tok/s/user steps) uniformly within that class's floor intervals. A class is a (row, answer) pair that passes measured H1 and LOO agreement on a floor interval at least 3 tok/s/user wide.
- **Band.** ≥ 2 options qualify; H1's margins hold on the engine's values as well as the measured ones; H2; no out-of-envelope step.
- **Pass.** Exact. **Debrief:** `StepCard` and the table for the winner and the runner-up (napkin, card, measured, `run_url`); the why: "per-GPU throughput rises with c until the floor bites; a bigger TP divides the bytes but not everything in a step, so TP 8 rarely wins per GPU". ### 7.3 E3 · `step/tp-speedup` (calibrated; S5-14; t6.l4; KC `t6.parallelism-composition`)

How much shorter a calibrated row's decode step gets from TP a to TP b at concurrency c, from the card with given parameters; exact to the family tolerance; fairness by the ratio rule (constant cover at the family tolerance ≤ 10 %, no span bound; S5-D57); the why shows the measured ratio for configurations with point claims (c 4, 1k/1k, TP 2 → 8: 17.41 → 9.11 ms, 1.91×). **Not an engine exercise** [proto]: over 123 published pairs (measured 1.08–2.99×; ratio LOO p90 9.5 %) the best constant, 1.398, is within 15 % on 56 % of pairs, so P(3 in a row within 10) = 63 %, far above 14 %.

### 7.4 E4 · `step/quant-bytes` (η-free, S5-10) and `step/quant-speedup` (calibrated on B200 NVFP4 TP 1–4, S5-14); t6.l5; KC `t6.fp4-capacity`

`quant-bytes`: the weight bytes in GB of a model at BF16, FP8 or NVFP4 (2, 1 and 0.5625 B per parameter; `serving.nvfp4.bits-per-weight`), the parameter count drawn as roofline draws `paramsB`; an absolute, so the span and constant-cover bounds hold; the ratio between precisions is shown in the why, not asked (a ratio of three precisions has at most 6 answers and spans at most 3.6×; S5-D57). `quant-speedup`: the card's FP8 → NVFP4 step ratio at a configuration, under the ratio rule; if it fails the cover bound it is cut as an item and stays the tab finding. The why: "1.78× fewer weight bytes, but measured TPOT falls only 1.01–1.32× at TP 1–4 (43 pairs [proto]): some per-step cost does not scale with weight bytes; this fit splits it between fixed terms and a lower η_m, and other equally good fits split it differently" (no fitted term named as the cause, S5-D5). **Not an engine exercise** [proto]: the best constant, 1.157, is within 15 % on 100 % of pairs (ratio LOO p90 6.0 %).

### 7.5 Also η-free (S5-10): `step/prefill-ms` and `step/ridge-kv`

- **`prefill-ms`** (t5.l3; `t5.prefill-vs-decode`): P tokens × 2·params ÷ F plus the attention term, at η = 1, on §7.2's feasible scenes (the P prompt tokens' KV within capacity). Its calibrated form (S5-14) ships only on TTFT-eligible rows, with the TTFT H4 label and no measured value in its why (no TTFT point claim backs it, S5-D18).
- **`ridge-kv`** (t4.l3; `t4.ridge-point`): decode intensity with KV, the napkin card's `flops ÷ memBytes` at tp 1 (one card, B5): (2·P·b + 4·layers·hidden·b·ctx) ÷ (2P + b·ctx·kv) at BF16, against the ridge. It tends to 2P ÷ (ctx·kv) + 4·layers·hidden ÷ kv; for Llama-3-8B BF16 (P = 8.03e9, 32 layers, hidden 4,096, kv = 131,072 B) that is 16.06e9 ÷ (2,048 × 131,072) + 4 = **63.8 FLOP/B** at a 2k context and 243.3 at 512, against H100's BF16 ridge of 989 ÷ 3.35 = **295.2**, so decode at a 2k context is never compute-bound on an H100 at any batch.

## 10. Task DAG for Sonnet implementers

### 10.1 How the PRs fit together

- **One PR per task into its integration branch**, as in Waves 1–3. Each task works in its own worktree; its prompt names the base sha and checks it with `git merge-base --is-ancestor`, because worktrees start at `master`. Each worktree makes a private hard-linked `node_modules`. The integrator merges a level before the next starts and runs every gate on the merged tree.
- **The stack is linear** (S5-D32): `wave-s5a` from 9aa27de; `wave-s5b` from s5a's merged tip. The owner merges in order. A task depends only on tasks of a lower level of its PR or of s5a.
- **File ownership.** Inside a level, tasks never touch the same file (dependencies inside a level are not allowed, because the runner runs a level in parallel). **Every file a task edits is listed, tests included.** No task edits `PLAN-100X.md` or a wave-3x file.
- **Generated files are never merged by hand.** The integrator regenerates them from the merged sources: `public/claims.json` (`verify-claims.ts --write`), `public/lessons-md/*.md` and `public/llms.txt` (`export-lessons-md.ts`), `src/data/search-index.json` (`build-search-index.ts`), `tests/fixtures/items/hashes/step.json` (`verify-generators --update-hashes --family step`), `src/data/claims/lazy/ix-points.ts` (`fetch-physics-points.ts --claims`), and `src/lib/world/physics/table.ts`, `docs/physics/{report,decisions}.json`, `src/data/physics/frontier-scenes.json` (`fit-physics.ts --write`), `docs/physics/controls.json` (`physics-controls.ts`).
- **The DAG was checked mechanically.** The task list below and `s5-dag.json` come from one data file, `tasks.py`, which checks: unique ids; dependencies that exist and never point forward or sideways; contiguous levels; disjoint files between the tasks of a level (generated files exempt); no `PLAN-100X.md` or wave-3x file; a learner-invisible s5a; every learner-facing task after the verdict (S5-07) or η-free; no fitted table in an η-free task; 2–12 hand-edited files; the browser flag on every UI check; a named pool for choice items; Level 2 tasks after the verdict, and no hard dependency of another task on a Level 2 task. It reports no problems.
- **Opus first** (S5-D43) marks a task whose method needs an Opus decision before (or while) a Sonnet implementer builds it: S5-00 (the protocol text and its block), S5-05 (`EngineV2`'s step order, stamping, box and envelope), S5-06 (replay weights, the fit, LOO) and S5-08 (decision-level H1, classes and guesser bounds).
